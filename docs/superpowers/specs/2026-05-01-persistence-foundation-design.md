# v2 持久化基础设施设计

## 1. 背景

当前 `v2` 主链路已经可运行，但运行时状态仍大量依赖进程内内存：

- 用户、会话、活动、参与者、申请、附件、审计记录在进程重启后会丢失
- `/devtools/health` 尚未返回真实依赖状态
- `storage.Store` 接口已定义，但尚未进入真实运行链路

本设计的目标不是扩展业务功能，而是把 `v2` 从“可演示”推进到“可持续运行”。

## 2. 目标

本轮完成后，系统应满足：

1. 服务重启后，核心业务数据不丢失。
2. refresh token 失效、登出、改密、重置密码不再依赖进程内状态。
3. 活动附件与头像不再保存在进程内内存中。
4. `/healthz` 与 `/api/v1/devtools/health` 能反映真实依赖状态。
5. 审计日志可持久化、查询、导出。
6. 现有前端主链路和 API 路径尽量不变。

## 3. 非目标

本轮明确不做：

- 旧系统到 `v2` 的任何数据迁移
- 双写、灰度切换、回填校验
- 活动动态字段 schema 系统
- 活动导入导出
- `/activities/new` 与 `/activities/:id/edit` 工作区重构
- 正式对象存储接入 `S3`/`MinIO`
- 消息队列、异步任务系统

由于已确认“无需迁移以前的数据”，本轮允许直接清库重建，只保留新 schema、seed 数据和新初始化逻辑。

## 4. 总体方案

采用“底座替换、业务契约尽量不变”的策略：

- `Postgres` 承担长期业务数据持久化
- `Redis` 承担短生命周期状态与失效控制
- `Storage` 先接本地磁盘适配器，保留统一接口以便后续切对象存储
- 业务模块边界保持 `backend/internal/modules/**` 现状，不重写服务层职责划分
- HTTP 路径和前端主链路尽量保持兼容

这是一次运行时基础设施替换，不是新一轮业务功能开发。

## 5. 数据归属

### 5.1 Postgres

以下数据进入 `Postgres`：

- `users`
  - 学生、教师、管理员基础资料
  - 账号状态
  - 密码哈希
  - 头像元数据
- `auth_refresh_sessions`
  - refresh token 会话主记录
  - 便于全局失效与审计
- `activities`
  - 标题、描述、分类、学年学期、状态、审核信息、拥有者
  - 动态字段 JSON
- `activity_participants`
  - 用户、活动、学分、加入时间
- `applications`
  - 自动生成的只读申请
  - 来源活动、学分、学年学期
- `files`
  - 附件与头像元数据
  - 包括 `storage_key`、大小、类型、上传者、归属资源
- `audit_logs`
  - 业务审计记录
  - 只追加，不前端删除
- `organization_*` / `option_*`
  - 组织树、年级、职称、学年、学期等配置

### 5.2 Redis

以下数据进入 `Redis`：

- refresh token 撤销标记或黑名单
- 用户级会话失效版本号
- 导入预校验结果绑定
  - 操作人
  - 导入类型
  - 文件哈希
  - 24 小时有效期
- 可选的登录限流键

原则是：短生命周期、可过期、用于控制而非业务归档的数据优先进 `Redis`。

### 5.3 Storage

以下二进制进入 `Storage`：

- 活动附件
- 用户头像

数据库仅保存元数据和 `storage_key`。下载和预览通过存储适配器读取内容。

首期只落本地磁盘适配器，但接口层面不封死实现类型。

## 6. 模块改造边界

### 6.1 保持不变的层

尽量保持：

- HTTP 路由结构
- 业务服务层对外能力
- 前端调用方式
- 活动状态机和申请自动生成规则

### 6.2 主要替换点

- `auth`
  - 从 `NewMemoryStore()` 切到 `repo + redis session state`
- `users`
  - 用真实数据库 repo 替换内存用户仓储
- `activities`
  - 用数据库 repo 替换内存活动仓储
- `participants`
  - 改为数据库 repo
- `applications`
  - 申请数据改为数据库持久化
  - 审核联动仍由服务层控制
- `files`
  - 从内存 `map` 改为 `files` 表 + `storage.Store`
- `audit`
  - 从内存 writer 改为数据库 append-only writer
- `dashboard`
  - 从运行时计数改为数据库聚合查询

### 6.3 测试专用内存实现

当前内存实现不应继续作为默认运行时依赖，但可以保留为测试 fake 或单元测试隔离组件。前提是：

- 不再由 `bootstrap.NewApp()` 直接装配
- 不再作为生产 compose 默认路径

## 7. 一致性与事务

以下流程必须放在数据库事务内：

1. 活动审核状态变更 + 申请生成、恢复、撤销
2. 活动创建基础数据落库
3. 参与者批量添加
4. 用户导入正式确认
5. 活动拥有者转移
6. 用户状态变更与会话失效版本更新

原则：凡是“一个业务状态变化后，另一个派生实体必须同步变化”的流程，都必须由事务保证，而不是依赖函数调用顺序。

## 8. 幂等要求

本轮需要明确保住以下幂等性：

- 审核接口重复提交不能重复生成申请
- 导入确认必须绑定同一预校验结果，重复确认要安全
- logout / revoke 重复调用不得造成脏状态
- 附件删除重复调用要返回稳定结果

幂等规则应优先由数据库唯一约束、状态检查和 Redis 绑定键共同保证。

## 9. 文件一致性策略

文件上传无法和数据库形成天然单事务，因此采用“元数据主导 + 补偿”策略。

### 9.1 上传

1. 先把文件写入 `Storage`
2. 成功后写入 `files` 表元数据
3. 若元数据写入失败，立即尝试删除刚写入的物理文件
4. 若物理删除也失败，记录错误日志，并保留后续清理入口

### 9.2 删除

首轮采用同步删除：

1. 先校验权限
2. 先删除物理文件
3. 物理删除成功后删除元数据

这样做的原因是：如果先删元数据再删物理文件，首轮没有异步清理机制时，容易产生不可追踪的悬空文件。

## 10. 健康检查与 Devtools

### 10.1 `/healthz`

供容器与反向代理使用。只要进程存活且核心依赖可达，就返回 `ok`。

最低检查项：

- `database`
- `redis`
- `storage`

### 10.2 `/api/v1/devtools/health`

供管理员页面使用，返回结构化详细状态：

- `database`
  - ping
  - 简单查询
- `redis`
  - `PING`
- `storage`
  - 根目录存在性与可写性
- `version`
  - 当前构建版本或 commit sha

### 10.3 Devtools 范围

本轮要求：

- 审计日志查询和导出改读持久化数据
- 运行日志接口至少给出真实来源，而不是固定空数组
- 浏览器内 API 测试器继续保持关闭状态，不在本轮开放执行能力

## 11. 审计要求

以下操作必须进入 `audit_logs`：

- 登录
- 登出
- 注册
- 用户创建、编辑、删除、状态变更、重置密码
- 活动创建、编辑、删除、提交、撤回、审核、复制、转移拥有者
- 导入预校验与正式确认
- 附件上传、删除
- Devtools 审计导出

审计日志至少满足：

- 只追加
- 不提供前端删除入口
- 支持按筛选条件查询与导出

## 12. 配置与初始化

本轮需要新增或确认以下能力：

- `Postgres` 连接配置
- `Redis` 连接配置
- 本地存储根目录配置
- migration 入口
- seed 入口
- 默认管理员初始化
- 组织和选项默认初始化

由于无需迁移旧数据，初始化逻辑应直接面向新 schema 设计，不保留兼容旧表结构的过渡代码。

## 13. 实施顺序

### 13.1 批次一：基础设施接线

- 接入 `Postgres`
- 接入 `Redis`
- 接入本地文件存储适配器
- 建 migration 和 seed 入口
- 改造 `/healthz` 和 `/devtools/health`

### 13.2 批次二：鉴权与用户

- 用户 repo 持久化
- refresh session 持久化
- 会话失效策略接入 Redis
- 头像元数据与文件存储接入

### 13.3 批次三：活动主链路

- 活动、参与者、申请切到数据库 repo
- 审核与申请联动改为事务
- 保持当前业务契约不变

### 13.4 批次四：文件与审计

- 附件切到 `files` 表 + `Storage`
- 审计切到数据库 append-only writer
- Devtools 审计查询与导出接持久化实现

### 13.5 批次五：验收与清理

- 用真实 `Postgres + Redis` 跑 `e2e`
- 跑 `make test-refactor`
- 跑 compose smoke
- 删除默认运行时对内存实现的依赖

## 14. 风险与控制

### 14.1 风险

- 持久化切换可能引入测试脆弱性
- 服务层原本依赖内存语义，切数据库后可能暴露状态边界问题
- 文件写入与元数据写入之间存在失败窗口
- 审计埋点不完整会导致设计承诺落空

### 14.2 控制措施

- 不改现有 HTTP 路径
- 每个批次先补测试，再替换实现
- schema 只做本轮闭环最小集
- 文件先用本地磁盘，避免对象存储变量
- 所有可重复请求的接口补幂等验证

## 15. 验收标准

本轮完成后，应至少验证：

1. 服务重启后用户、活动、参与者、申请、附件元数据、审计记录不丢。
2. refresh token 失效逻辑不依赖进程内内存。
3. 附件与头像不依赖进程内内存。
4. 审计日志可查询、可导出、可持久化。
5. `/healthz` 与 `/api/v1/devtools/health` 返回真实依赖状态。
6. 当前前端主链路无需因本轮改造发生大规模返工。

## 16. 结论

这一轮的本质不是“继续补功能”，而是先把 `v2` 的运行底座做实：

- 真实数据库
- 真实 Redis
- 真实文件存储
- 真实健康检查
- 真实审计持久化

完成这一轮后，后续再补活动动态字段、导入导出、编辑工作区等业务深水区，返工风险会显著更低。
