# 学分活动管理系统重构需求文档

> 文档定位：本文件基于当前仓库代码实现反向梳理系统需求，作为后续重构的功能基线。
> 约束原则：以当前实际代码行为为准；若 README、页面文案、接口命名与代码行为不一致，以服务端与前端现有实现为最高优先级。
> 适用范围：`frontend`、`api-gateway`、`auth-service`、`user-service`、`credit-activity-service`、`database`。

## 1. 文档目标

本需求文档用于明确当前系统已经实现或部分实现的业务能力、用户角色、页面行为、接口边界、数据约束和非功能要求，为重构提供可验证的“现状基线”。

重构后的系统至少应满足以下目标：

- 保留现有已上线功能的核心业务语义和主要业务路径。
- 保留现有角色权限模型，除非需求明确升级。
- 保留核心业务约束，但不要求兼容现有数据库结构、字段类型或接口返回格式。
- 显式识别当前实现中的不一致、未完成项和技术债，供重构时统一收敛。

### 1.1 已确认的重构原则

- 本次重构包含前端与后端，允许重新设计前端界面逻辑、页面结构与 API 契约，不要求兼容现有前端实现。
- 后端目标架构确定为单体应用，采用模块化设计承载认证、用户、活动、申请、附件和管理能力，不再保留原有微服务拆分形态。
- 本次重构允许清库重建，不要求兼容现有数据库表结构、字段类型、主键类型或历史数据迁移。
- 当前数据库模型仅作为业务语义参考，不作为目标实现的强约束。
- 系统必须移除所有开发/测试旁路鉴权能力，包括 `TEST_DATA_MODE` 开放接口和 `X-Internal-Service` 系统用户旁路。
- 申请继续定义为“活动审核通过后自动生成的只读凭证”，不扩展为学生自主提交申请流程。
- 活动、参与者、附件的结构性编辑统一限定为 `draft` 状态。
- 本轮移除独立权限管理子系统，只保留固定角色 `student`、`teacher`、`admin`。
- 首期只保留固定活动分类模板能力，“保存为模板”不纳入本轮完整实现范围。
- 审核意见定义为可选字段，不强制在通过、拒绝或修改审核状态时填写。
- 学分规则统一为大于等于 0，不设置固定上限。
- 文件存储采用存储抽象层，默认支持本地开发存储，并允许在部署时切换到对象存储。
- 主业务实体主键采用时序友好的全局唯一 ID 方案，使用 ULID 或雪花类方案，不再以现有 UUID 设计为目标约束。

## 2. 系统概述

本次重构目标系统仍然面向高校“双创分/学分活动”管理场景，核心目标仍是支持活动创建、审核、参与者管理、附件管理、自动生成申请和统计查询，但技术形态调整为“前端 + 模块化单体后端”。

系统由以下模块构成：

- 前端 Web 应用：负责登录、注册、列表、详情、资料管理和管理员开发工具。
- 单体后端应用：统一承载认证、用户、活动、参与者、附件、申请、搜索、统计和后台治理能力。
- PostgreSQL：主业务数据库。
- Redis：认证黑名单、限流和可选缓存能力。
- 文件存储：通过抽象层接入本地文件系统或对象存储。

## 3. 用户角色与权限模型

系统存在三种基础角色：

- `student`：学生。
- `teacher`：教师。
- `admin`：管理员。

### 3.1 权限总览

学生可执行的核心动作：

- 登录、登出、刷新登录状态。
- 自助注册学生账号。
- 查看和编辑自己的个人资料。
- 修改自己的密码。
- 查看自己创建的活动。
- 查看自己参与的活动。
- 创建活动草稿。
- 编辑自己拥有的草稿活动。
- 提交自己拥有的草稿活动进入审核。
- 撤回自己提交的活动。
- 删除自己拥有且仍处于草稿状态的活动。
- 作为活动拥有者，在草稿状态下管理参与者和附件。
- 查看自己的申请记录。

教师可执行的核心动作：

- 拥有所有认证用户的通用能力。
- 查看学生列表与学生统计。
- 查看活动列表、待审核活动、活动详情、申请列表。
- 审核活动，可将活动状态置为通过或拒绝。
- 在 `approved` 与 `rejected` 之间再次修改审核结果。
- 转移任意未删除活动的拥有者。
- 删除参与者、设置参与者学分、上传和删除附件。
- 查看全部申请。
- 导出活动、参与者、申请数据。
- 生成活动统计报表。

管理员可执行的核心动作：

- 拥有教师全部能力。
- 查看教师列表与教师统计。
- 创建、编辑、删除学生和教师。
- 批量导入、导出、批量删除、批量改状态、重置密码。
- 删除任意活动。
- 访问开发者工具页面。
- 查看系统状态、运行日志和业务审计日志。

### 3.2 权限实现原则

- 后端统一完成 JWT 解析、身份恢复和角色校验。
- 角色模型固定为 `student`、`teacher`、`admin`，本轮不引入可配置 RBAC。
- 对于“活动所有者”这类依赖业务数据的权限，必须在业务层基于数据库判断，不能仅依赖静态角色判断。

## 4. 认证与会话需求

### 4.1 登录

系统必须支持以下登录标识之一配合密码登录：

- 用户名 `username`
- 学号 `student_id`
- 工号 `teacher_id`

登录成功后必须返回：

- `token`
- `refresh_token`
- 当前用户基础信息

登录失败时必须区分以下情况：

- 参数不完整或格式错误。
- 用户不存在或密码错误。
- 账号状态不是 `active`。

### 4.2 Token 机制

- 访问 token 使用 JWT，默认有效期 24 小时。
- refresh token 使用 JWT，默认有效期 7 天。
- token payload 至少包含 `user_id`、`username`、`user_type`、`exp`、`iat`。
- 前端必须在请求头中以 `Authorization: Bearer <token>` 方式携带 token。

### 4.3 Token 刷新

- 当接口返回 401 时，前端应尝试使用 `refresh_token` 调用刷新接口。
- 刷新成功后应更新本地 token 并自动重试原请求。
- 刷新失败后应清理本地认证信息并跳转到登录页。
- 系统必须具备 refresh token 统一失效能力。
- 当用户修改密码、管理员重置密码，或账号状态变为 `inactive` / `suspended` 时，必须立即使该用户全部 refresh token 失效，并要求重新登录。

### 4.4 登出

- 登出应将当前 access token 放入 Redis 黑名单，直到其自然过期。
- 前端登出时即使后端接口失败，也必须清理本地认证信息。

### 4.5 登录安全

- 登录接口必须启用基于 Redis 的限流。
- 当前实现为按 IP 与用户名双重限制，默认 1 分钟内最多 5 次尝试。
- 新系统不再允许任何基于环境变量的无鉴权旁路登录或内部服务伪装身份。

## 5. 用户域需求

### 5.1 用户模型

系统使用统一用户表存储学生、教师、管理员。

用户公共字段至少包括：

- `id`
- `username`
- `password`
- `email`
- `phone`
- `real_name`
- `user_type`
- `status`
- `avatar`
- `department_id`
- `last_login_at`
- `created_at`
- `updated_at`
- `deleted_at`

学生特有字段：

- `student_id`
- `grade`

教师特有字段：

- `teacher_id`
- `title`

### 5.2 用户状态

系统必须支持以下用户状态：

- `active`
- `inactive`
- `suspended`

认证模块只允许 `active` 状态用户登录和通过 token 验证。

当账号状态变为 `inactive` 或 `suspended` 时，系统必须立即使该用户全部 refresh token 失效。

### 5.3 学生注册

系统必须支持学生自助注册。

注册时必须满足：

- 用户名唯一。
- 邮箱唯一。
- 手机号唯一。
- 学号唯一。
- 密码满足复杂度规则。
- 手机号格式合法。
- 学号必须是 8 位数字。
- 年级必须是 4 位数字。
- 必须能定位到一个合法班级。

学生注册必须支持两种班级定位方式：

- 直接传 `department_id`。
- 传入 `college` + `major` + `class`，后端反查班级并校验层级关系。

### 5.4 管理员创建学生/教师

管理员必须能够创建学生和教师账号。

创建学生时必须：

- 强制要求 `user_type=student`。
- 强制提供合法 `student_id`。
- 强制绑定班级。

创建教师时必须：

- 强制要求 `user_type=teacher`。
- 强制提供合法 `teacher_id`。
- 强制绑定学部。

### 5.5 用户资料查看

系统必须支持：

- 当前登录用户查看自己的完整资料。
- 管理员查看任意用户详情。
- 教师查看学生详情。
- 学生不得查看其他学生或教师详情。

当前实现通过数据库视图返回更完整的学生/教师信息：

- `student_complete_info`
- `teacher_complete_info`

### 5.6 用户资料编辑

系统必须支持当前用户编辑自己的以下信息：

- 邮箱
- 手机号
- 真实姓名
- 头像
- 年级
- 教师职称
- 所属学部/专业/班级

管理员还必须能够更新指定用户状态、学号、工号及其他资料。

### 5.7 密码管理

系统必须支持：

- 用户自助修改密码，需校验原密码。
- 管理员重置指定用户密码。

新密码必须满足复杂度校验。

无论是用户自助修改密码还是管理员重置密码，系统都必须立即使该用户全部 refresh token 失效，并要求重新登录。

### 5.8 头像管理

系统必须支持上传和删除头像。

头像要求：

- 仅允许图片类型。
- 前端当前限制最大 5MB。
- 头像必须通过受控访问或短期签名 URL 提供，不得暴露长期公开静态地址。
- 头像签名 URL 默认有效期为 1 小时。
- 头像被替换或删除后，旧签名 URL 必须立即失效。

### 5.9 用户搜索与列表

系统必须支持按用户类型搜索用户，仅支持搜索：

- 学生
- 教师

学生列表必须支持筛选：

- 关键字
- 学部
- 专业
- 班级
- 年级
- 状态

教师列表必须支持筛选：

- 关键字
- 学部
- 职称
- 状态

学生不能搜索教师。

### 5.10 用户统计

系统必须支持：

- 全局用户统计。
- 学生统计。
- 教师统计。

统计维度至少包括：

- 用户总数
- 活跃用户数
- 各角色人数
- 新增用户数
- 学生按学部/专业/年级分布
- 教师按学部/职称分布

统计口径要求：

- `活跃用户数` 默认定义为最近 30 个自然日内成功登录过的 `active` 用户数。
- `新增用户数` 默认定义为当前自然月内创建的用户数；若报表接口显式传入时间范围，则以时间范围为准。
- 所有统计都必须自动叠加当前用户可见范围和软删除过滤条件。

### 5.11 用户导入导出

管理员必须能够：

- 下载用户导入模板。
- 导入学生或教师数据。
- 导出用户数据。

导入要求：

- 支持 `csv`、`xls`、`xlsx`。
- 校验文件类型、大小和字段合法性。
- 导入流程分为“预校验”和“正式导入”两步。
- 预校验阶段不得落库，必须返回逐行预览结果与错误明细。
- 预校验结果必须绑定操作人、导入类型和文件哈希，默认 24 小时内有效。
- 正式导入必须由用户显式确认触发。
- 正式确认时必须使用与预校验完全相同的文件。
- 正式导入必须采用整批事务模式，任一行失败则整批回滚。
- 对同一份已确认导入的文件重复提交确认请求时，系统必须保证幂等。

导出要求：

- 当前主格式为 Excel。
- 导出内容应按用户类型填充学部/专业/班级等层级信息。

## 6. 组织架构与选项配置需求

系统必须维护学校组织结构配置，用于表单下拉、注册校验和用户资料映射。

组织结构层级为：

- 学校
- 学部 `college`
- 专业 `major`
- 班级 `class`

系统还必须提供以下选项配置：

- 年级
- 学年
- 学期
- 用户状态
- 教师职称

选项接口必须是前端多个页面的统一数据源，并允许前端做缓存。

## 7. 活动域需求

### 7.1 活动模型

活动实体至少包含以下字段：

- `id`
- `title`
- `description`
- `start_date`
- `end_date`
- `status`
- `category`
- `academic_year`
- `semester`
- `owner_id`
- `reviewer_id`
- `review_comments`
- `reviewed_at`
- `details`
- `created_at`
- `updated_at`
- `deleted_at`

其中 `details` 为 JSONB，用于承载活动分类驱动的扩展字段。

`start_date` 与 `end_date` 必须定义为纯日期字段，统一按 `Asia/Shanghai` 时区解释。

### 7.2 活动状态机

系统必须支持以下活动状态：

- `draft`
- `pending_review`
- `approved`
- `rejected`

状态流转要求：

- 新建活动默认进入 `draft`。
- 只有活动拥有者可以把 `draft` 提交为 `pending_review`。
- 只有活动拥有者可以把 `pending_review` 或 `rejected` 撤回为 `draft`。
- 教师或管理员可以把 `pending_review` 审核为 `approved` 或 `rejected`。
- 教师或管理员只能在 `approved` 与 `rejected` 之间再次修改审核结果，不能改回 `draft` 或 `pending_review`。

审核意见规则：

- 审核意见为可选字段。
- 审核通过、拒绝、修改审核状态都可以不填写审核意见。
- 若填写审核意见，系统应保留最近一次审核操作的意见和时间。

### 7.3 活动基础规则

活动必须满足：

- 标题非空。
- 分类非空。
- 学年非空。
- 学期非空。
- 开始日期和结束日期合法。
- 结束日期不能早于开始日期。
- 结束日期按包含当天解释。

### 7.4 活动分类

系统当前内置活动分类：

- 创新创业实践活动
- 学科竞赛
- 大学生创业项目
- 创业实践项目
- 论文专利

### 7.5 活动分类动态字段

系统必须支持按活动分类动态渲染附加字段，并写入 `details`。

动态字段必须采用 schema 驱动，至少为每个字段定义以下元数据：

- `key`
- `label`
- `type`
- `required`
- `default_value`
- `options_source`
- `validation_rules`
- `display_order`

字段类型至少支持：

- `text`
- `textarea`
- `number`
- `select`

当前分类字段定义要求如下：

- 创新创业实践活动：主办单位 `text` 必填；成果描述 `textarea` 选填。
- 学科竞赛：竞赛名称 `text` 必填；竞赛级别 `select` 必填，枚举来源于配置；奖项等级 `select` 选填，枚举来源于配置；排名 `text` 选填。
- 大学生创业项目：项目阶段 `select` 必填，枚举来源于配置；经费 `number` 选填，最小值为 `0`。
- 创业实践项目：实践类型 `select` 必填，枚举来源于配置；时长 `number` 选填，最小值为 `0`。
- 论文专利：名称 `text` 必填；类别 `select` 必填，枚举来源于配置；作者排名 `number` 选填，最小值为 `1`。

前后端必须共享同一份动态字段 schema，不允许页面硬编码与后端校验规则分离。

### 7.6 活动创建

所有认证用户都必须能够创建活动草稿。

创建活动时：

- `owner_id` 必须为当前登录用户。
- `status` 固定为 `draft`。
- 必须填写 `academic_year` 与 `semester`。
- 可携带 `details`。

### 7.7 活动编辑

重构后活动编辑规则确定为：

- 只有 `draft` 状态的活动允许编辑基础信息和 `details`。
- 活动拥有者、教师、管理员都可以编辑任意 `draft` 活动。
- 非 `draft` 活动不允许编辑基础信息、动态字段、参与者和附件。
- 教师和管理员在活动域拥有完整管理权限，但“提交审核”和“撤回到草稿”仍归活动拥有者执行。
- 教师和管理员可以转移任意未删除活动的 `owner_id`。
- 转移拥有者后，原拥有者失去基于“活动拥有者”身份的专属操作权限，新拥有者立即获得相应权限。
- 转移拥有者必须写入业务审计日志。

### 7.8 活动查看范围

学生只能看到：

- 自己创建的活动。
- 自己参与的活动。

教师和管理员可以看到：

- 全部活动。

学生访问单个活动详情时，若既不是拥有者也不是参与者，必须被拒绝。

### 7.9 活动删除

重构后删除规则确定为：

- 教师和管理员可以删除任意活动。
- 活动拥有者可以删除自己处于 `draft` 状态的活动。
- 活动拥有者不能删除非 `draft` 活动，只能按状态规则执行撤回。

删除活动时必须同时软删除：

- 参与者记录
- 申请记录
- 附件记录

若附件物理文件未被其他活动复用，还需删除物理文件。

### 7.10 活动复制

系统必须支持复制活动。

复制权限要求：

- 活动拥有者可以复制自己的活动。
- 教师和管理员可以复制任意活动为自己的草稿副本。

复制后的活动应：

- 标题追加“(副本)”。
- 状态重置为 `draft`。
- 所有者改为当前用户。
- 复制基础信息与 `details`。
- 复制参与者记录。
- 复制附件记录；如底层文件采用去重存储，可复用物理文件并增加引用计数，不要求复制物理文件本体。
- 不复制审核人、审核意见、审核时间和申请记录。

### 7.11 活动模板

首期只保留固定活动分类模板能力，用于驱动活动分类、动态字段 schema 和表单默认配置。

本轮不补“保存为模板”能力，不引入用户自定义模板持久化、模板列表管理或模板复用链路。

### 7.12 活动列表与搜索

活动列表必须支持：

- 分页
- 关键字查询
- 按状态筛选
- 按分类筛选
- 按学年筛选
- 按学期筛选
- 按所有者筛选

活动搜索接口还必须支持：

- 开始日期范围
- 结束日期范围
- 排序字段
- 排序方向

### 7.13 待审核活动

教师和管理员必须能够查询待审核活动列表。

### 7.14 活动统计与报表

系统必须提供活动统计能力，至少包括：

- 活动总数
- 草稿数量
- 待审核数量
- 已通过数量
- 已拒绝数量
- 参与者总数
- 总学分

活动报表必须支持：

- 月度报表
- 分类报表
- 状态报表
- 学年报表
- 学期报表

### 7.15 活动导入导出

系统必须支持活动导入导出。

导入要求：

- 支持 CSV 和 Excel。
- 最大支持 1000 行数据。
- 必须包含 `title`、`description`、`start_date`、`end_date`、`category`、`academic_year`、`semester`。
- 导入活动默认归属当前登录用户，状态为 `draft`。
- 导入流程分为“预校验”和“正式导入”两步。
- 预校验阶段不得落库，必须返回逐行预览结果与错误明细。
- 预校验结果必须绑定操作人、导入类型和文件哈希，默认 24 小时内有效。
- 正式导入必须由用户显式确认触发。
- 正式确认时必须使用与预校验完全相同的文件。
- 正式导入必须采用整批事务模式，任一行失败则整批回滚。
- 对同一份已确认导入的文件重复提交确认请求时，系统必须保证幂等。

导出要求：

- 支持 JSON、CSV、Excel。
- 支持按分类、状态、学年、学期、起止日期筛选。

## 8. 参与者管理需求

- `activity_id`
- `user_id`
- `credits`

### 8.2 参与者身份限制

### 8.3 参与者管理权限

以下角色可以管理参与者：

- 活动拥有者
- 教师
- 管理员

学生参与者本人只允许在 `draft` 状态执行“退出活动”。

### 8.4 参与者编辑时机

参与者编辑规则确定为：

- 只有 `draft` 状态允许新增、删除、批量删除和修改学分。
- 学生参与者本人退出活动同样视为结构性修改，只允许在 `draft` 状态执行。
- 非 `draft` 状态只能查看，不允许结构性修改。

### 8.5 参与者操作

- 删除单个参与者
- 批量删除参与者

- 批量设置参与者学分

- 导出参与者列表
- 查询当前用户参与过的活动

### 8.6 参与者学分规则

### 8.7 参与者统计

- 参与者总数

## 9. 申请域需求

### 9.1 申请模型

申请记录至少包含：

- `id`
- `activity_id`
- `user_id`
- `status`
- `applied_credits`
- `awarded_credits`
- `submitted_at`
- `created_at`
- `updated_at`
- `deleted_at`

申请详情、搜索、导出和统计必须同时暴露从所属活动继承的 `academic_year` 与 `semester` 只读维度，不允许在申请域独立编辑这两个字段。

### 9.2 申请生成机制

系统不支持手工提交申请，也不计划在本轮重构中引入该能力。

申请的来源是：

- 当活动首次从非 `approved` 状态变为 `approved` 时，系统自动为全部参与者生成申请。

申请生成规则：

- 每个活动与用户组合只能有一条申请。
- 若历史申请被软删除，再次通过时应恢复该申请。
- `applied_credits` 与 `awarded_credits` 默认等于参与者当前学分。
- 申请状态当前固定为 `approved`。
- 申请为只读记录，学生、教师、管理员均不能手工创建、编辑或审批申请。
- 活动审核状态变更与申请生成、恢复、撤销必须在同一数据库事务内完成。
- 对同一活动的重复审核请求和失败重试必须具备幂等性，不得生成重复申请或留下中间状态。

### 9.3 申请撤销

当活动从 `approved` 变为其他状态时，系统必须在同一事务中软删除该活动关联的申请记录。

### 9.4 申请查看范围

学生只能看到自己的申请。

教师和管理员可以看到：

- 全部申请列表
- 指定申请详情

### 9.5 申请查询能力

系统必须支持：

- 当前用户申请列表
- 全部申请列表
- 单个申请详情
- 申请统计
- 申请导出
- 申请搜索

搜索条件至少包括：

- 关键字
- 活动 ID
- 用户 ID
- 状态
- 学年
- 学期
- 起止日期
- 学分范围

申请不单独维护附件实体。

申请详情页中的附件展示与下载，实际指向该申请所关联活动的附件列表，并沿用活动附件的访问控制规则。

### 9.6 申请统计

系统当前保留的统计结构包括：

- 申请总数
- 待处理数
- 已通过数
- 已拒绝数
- 获批总学分

由于当前真实申请状态只有 `approved`，`pending` 和 `rejected` 统计属于预留能力。

申请统计必须支持按学年和学期聚合与筛选。

### 9.7 申请导出

系统必须支持导出申请列表。

当前实现现状：

- JSON 导出可用。
- v2 重构已补齐 CSV 和 Excel 导出接口，前端默认触发 Excel 导出。

后续维护时应保持导出字段与申请列表、搜索条件、学年和学期维度一致。

导出内容必须包含所属活动的学年和学期。

## 10. 附件管理需求

### 10.1 附件模型

附件实体至少包含：

- `id`
- `activity_id`
- `file_name`
- `original_name`
- `file_size`
- `file_type`
- `file_category`
- `description`
- `uploaded_by`
- `uploaded_at`
- `download_count`
- `md5_hash`

### 10.2 附件权限

附件列表、下载和预览必须完全继承所属活动的访问控制规则。

只有在有权查看所属活动时，用户才可以：

- 查看活动附件列表
- 下载附件
- 预览支持预览的附件

以下角色可以管理附件：

- 活动拥有者
- 教师
- 管理员

### 10.3 附件编辑时机

附件编辑规则确定为：

- 只有 `draft` 状态允许上传、批量上传、修改描述和删除附件。
- 非 `draft` 状态只能查看、下载和预览附件。

### 10.4 文件类型与大小

系统必须支持多类附件：

- 文档
- 图片
- 视频
- 音频
- 压缩包
- 表格
- 演示文稿

单文件大小上限在新系统中允许重定义，但必须作为统一配置项由前后端共享。

系统必须校验：

- 文件扩展名是否在允许列表中。
- MIME 类型是否与扩展名匹配。

### 10.5 附件上传

系统必须支持：

- 单文件上传
- 批量上传，最大 10 个文件

上传时必须：

- 生成 MD5。
- 写入数据库记录。
- 通过统一存储抽象层保存文件。

重构后要求：

- 本地开发环境默认可使用本地文件系统。
- 部署环境应支持切换为对象存储。
- 文件命名、去重、引用计数和删除策略必须统一，不再允许单文件上传和批量上传采用不同规则。

### 10.6 附件去重与复用

当前实现存在如下语义：

- 单文件上传会按 MD5 尝试复用物理文件。
- 批量上传会校验同一活动内重复文件。
- 删除附件时，如果其他活动仍引用相同 MD5，则保留物理文件。

### 10.7 附件预览

系统必须支持预览以下类型：

- PDF
- JPG/JPEG
- PNG
- GIF
- TXT

其他类型应返回“不支持预览”。

### 10.8 附件统计

附件列表接口返回时应同时提供：

- 总附件数
- 总大小
- 按分类计数
- 按文件类型计数

## 14. 数据库与数据约束需求

### 14.1 主键与删除策略

- 主业务实体主键采用时序友好的全局唯一 ID 方案，优先使用 ULID 或雪花类设计。
- 关联实体可根据查询与存储需求独立设计主键与外键类型。
- 用户、活动、参与者、申请、附件应保留软删除能力，除非重构设计另行论证并统一替换。

### 14.2 唯一性约束

用户侧必须保持以下唯一约束：

- 用户名唯一
- 邮箱唯一
- 手机号唯一
- 学号唯一
- 工号唯一

软删除后的复用策略：

- 用户名、学号、工号不可复用。
- 邮箱和手机号在原记录软删除后可以复用。

参与者侧必须保持以下唯一约束：

- 同一活动下，未删除状态的同一用户只能有一条参与者记录。

申请侧必须保持以下唯一约束：

- 同一活动下，同一用户只能有一条申请记录。

### 14.3 业务校验约束

数据库层至少应保留：

- 活动结束日期不得早于开始日期。
- 用户身份与学号/工号字段组合必须一致。
- 附件大小上限校验。
- 附件类型限定。
- 学分不得小于 0。

### 14.4 视图需求

数据库应保留用于查询聚合的视图或同等查询能力：

- 学生基本/详细/完整信息视图。
- 教师基本/详细/完整信息视图。
- 活动详情视图。
- 申请详情视图。

## 15. 非功能需求

### 15.1 架构

- 系统必须维持前后端分离与服务边界清晰。
- 后端采用模块化单体架构，业务边界在代码模块和领域层内清晰表达。

### 15.2 可维护性

- 配置项必须外置，至少包括数据库连接、Redis 连接、JWT Secret、存储后端配置和选项配置路径。
- 动态下拉选项和活动动态字段应继续由配置驱动，而不是硬编码在多个页面。

### 15.3 性能

- 列表接口必须支持分页。
- 列表接口应尽量返回轻量聚合信息，避免无必要的关联数据加载。
- 前端应缓存不经常变化的 options。

### 15.4 可用性

- 前端请求默认 15 秒超时。
- 服务必须提供健康检查接口。
- Docker Compose 部署应可一键启动整个系统。

### 15.5 安全

- 所有敏感接口必须要求认证。
- 管理员能力必须明确隔离。
- 不得向前端暴露密码哈希。
- 上传文件必须校验类型和大小。
- 前端不得开放 API 测试器入口，调试统一走正式鉴权、服务日志和业务审计日志。

### 15.6 可观测性

- 服务必须输出结构化或可读日志。
- 后端至少提供健康检查和关键依赖状态检查。
- 管理员可通过前端查看运行日志。
- 面向前端展示的日志必须完成敏感信息脱敏。

### 15.7 业务审计

- 系统必须维护独立于运行日志的业务审计日志。
- 审计日志至少覆盖登录、用户创建/编辑/删除/重置密码、活动审核/删除/拥有者转移、导入导出、附件删除和调试开关变更。
- 每条审计日志至少记录操作者、目标对象类型、目标对象 ID、动作、时间、结果、来源 IP 和摘要变更。
- 审计日志至少保留 1 年。
- 审计日志采用只追加模式，不提供前端编辑或删除入口。
- 审计日志支持按筛选结果导出。

## 16. 当前实现中的重要遗留项与已确认收敛方向

以下内容不是“未来可选优化”，而是重构时必须明确决策的现状问题。

### 16.1 JWT claims 字段不一致

旧系统存在两种用户 ID claim 读取方式：

- 旧网关与旧认证服务使用 `uuid`
- 旧用户服务部分工具函数读取 `id`

这会导致某些依赖 `GetCurrentUserID` 的逻辑有潜在兼容风险。新系统为模块化单体，重构时必须统一 claim 结构，并统一使用 `user_id` 作为 token 中的用户主键字段名。

### 16.2 活动域权限与状态规则已确认收敛方向

已确认的目标规则如下：

- 只有 `draft` 状态允许编辑活动、参与者和附件。
- 活动拥有者、教师、管理员都可以编辑任意 `draft` 活动。
- 活动拥有者可以把 `pending_review` 和 `rejected` 撤回为 `draft`。
- 教师和管理员在活动域拥有完整管理权限。

### 16.3 申请模型已确认收敛方向

已确认申请继续维持为：

- 活动审核通过后自动生成。
- 只读凭证记录。
- 非独立审批工作流。
- 不支持学生自主发起申请。

### 16.4 开发/测试旁路鉴权将被移除

以下能力不进入新系统：

- `TEST_DATA_MODE` 下开放的无鉴权测试数据接口。
- `X-Internal-Service` 触发的系统管理员旁路身份。

新系统统一走正式鉴权链路。

### 16.5 权限子系统将被移除

旧系统网关暴露了 `/permissions` 相关接口，但前端未形成完整权限管理能力。

已确认新系统不保留独立权限管理子系统，只保留固定角色模型。

### 16.6 导出能力完成状态

v2 重构已补齐以下原占位能力：

- 申请 CSV/Excel 导出
- 参与者 Excel 导出
- 活动 CSV/Excel 导出

后续若新增导出字段，必须同步更新 CSV、Excel、前端下载入口与测试。

### 16.7 模板能力未闭环

活动模板相关接口和页面认知存在，但缺少完整模板实体和使用链路。

已确认首期只保留固定分类模板，不补完“保存为模板”链路。

### 16.8 附件命名和去重策略不统一

单文件上传与批量上传对物理文件命名不同，去重策略也不完全一致。重构时应统一。

### 16.9 默认账号初始化来源存在重叠

旧数据库初始化脚本和旧认证模块都可能创建管理员账号。重构时应保留单一初始化入口。

### 16.10 前端开发工具中的部分接口定义与后端真实路由不完全一致

例如开发工具中出现 `/api/auth/register`、`/api/auth/refresh` 等路径文案，但真实后端分别为学生注册和 `/api/auth/refresh-token`。重构时应同步文档、UI 模板和真实接口。

## 17. 重构验收基线

重构完成后，应至少验证以下关键业务场景：

- 学生注册成功并能登录。
- 已注册用户能登录、刷新 token、登出。
- 管理员能创建学生与教师。
- 学生能创建草稿活动、编辑、提交审核、撤回、删除草稿。
- 教师或管理员能审核活动。
- 活动拥有者能把待审核和已拒绝活动撤回到草稿。
- 活动通过后自动生成申请。
- 活动从通过改为其他状态后，申请被撤销。
- 教师或管理员可以转移任意未删除活动的拥有者，且权限即时切换并写入审计日志。
- 活动拥有者可以复制自己的活动，教师和管理员可以复制任意活动为自己的草稿副本。
- 草稿活动能管理参与者和附件。
- 学生只能查看自己有权限的活动和申请。
- 教师和管理员能查看全量活动与申请。
- 用户、活动、参与者、申请、附件的搜索、分页、导入导出可用，且活动与申请均支持学年/学期维度。
- 头像签名 URL 在头像替换或删除后立即失效。
- 导入预校验结果与正式确认导入之间的文件绑定和重复确认幂等生效。
- 管理员开发工具可查看系统状态、运行日志和业务审计日志。

## 18. 建议的重构边界

为避免“边重构边改需求”导致失控，建议将本项目重构拆成以下三个层次：

- 第一层：重定义数据模型、接口契约和前端信息架构，同时保留本文件确认的核心业务语义。
- 第二层：统一状态机、导出能力、token claims、ID 方案和文件存储策略。
- 第三层：视需要补充权限前端、模板体系和更复杂的后台治理能力。

## 19. Brainstorm 复查后的补充确认结论

本轮补充确认的收敛结果如下：

- token payload 统一使用 `user_id` 作为用户主键字段名。
- 活动复制时复制基础信息、`details`、参与者和附件，但不复制审核信息和申请记录。
- 活动分类动态字段改为 schema 驱动，字段类型、必填性、枚举来源、默认值和校验规则都必须显式定义。
- 教师和管理员只能在 `approved` 与 `rejected` 之间再次修改审核结果，不能改回 `draft` 或 `pending_review`。
- 活动审核状态变更与申请生成、恢复、撤销必须同事务执行，并保证接口幂等。
- 申请页中的附件能力统一解释为“查看和下载关联活动的附件”。
- 生产环境保留健康检查和脱敏日志查看，前端 API 测试器全部移除。
- 统计指标口径在需求阶段固化，不再留到实现阶段自由定义。
- 正文中的活动模板章节统一按“固定分类模板、无自定义模板能力”执行。

## 20. 第三轮 Brainstorm 复查后的补充确认结论

本轮补充确认的收敛结果如下：

- 附件列表、下载和预览完全继承所属活动可见性。
- 学生参与者本人只能在 `draft` 状态退出活动。
- 用户修改密码、管理员重置密码、账号转为 `inactive` / `suspended` 时，必须立即使该用户全部 refresh token 失效。
- 导入统一采用“预校验 + 显式确认 + 正式整批事务导入”模式。
- 用户名、学号、工号不可复用；邮箱和手机号在原记录软删除后可以复用。
- 系统必须新增独立业务审计日志，覆盖关键管理和高风险业务操作。
- 活动日期字段统一定义为按 `Asia/Shanghai` 解释的纯日期，结束日期包含当天。
- 头像改为受控访问或短期签名 URL，不再提供长期公开静态地址。
- 学年与学期正式纳入活动创建、查询、导入导出、统计和报表维度。

## 21. 第四轮 Brainstorm 复查后的补充确认结论

本轮补充确认的收敛结果如下：

- 教师和管理员可以转移任意未删除活动的拥有者，并同步权限与审计记录。
- 活动拥有者可以复制自己的活动；教师和管理员可以复制任意活动为自己的草稿副本。
- 申请域继承所属活动的学年与学期，并支持详情展示、搜索、导出和统计。
- 审计日志至少保留 1 年，采用只追加模式，不提供前端编辑或删除入口，并支持按筛选结果导出。
- 头像签名 URL 默认有效期为 1 小时，头像替换或删除后旧 URL 必须立即失效。
- 导入预校验结果必须绑定操作人、导入类型和文件哈希，默认 24 小时内有效；正式确认时必须使用同一文件，并保证重复确认幂等。
